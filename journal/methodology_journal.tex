\section{Evaluation Methodology}
\label{sec:methodology}

Our evaluation examines three aspects of the tool: the accuracy of inferred specifications against documented or manually written specifications, the effectiveness of specification-guided test generation compared with baseline approaches, and how inference effectiveness varies across method categories.

\subsection{Subject Selection}

We selected Apache Commons Lang 3.14 as our evaluation subject for its diversity of method types, extensive Javadoc documentation (enabling validation), maturity, deterministic pure functions (ideal for mutation testing), and research precedent~\cite{pacheco2007randoop, fraser2011evosuite}. From it, we selected 11 classes covering all method categories: \texttt{NumberUtils}, \texttt{BooleanUtils}, \texttt{CharUtils} (Utility); \texttt{MutableInt}, \texttt{MutableDouble}, \texttt{MutableBoolean} (State Modification); \texttt{Pair}, \texttt{MutablePair} (Factory/Delegate); \texttt{Validate}, \texttt{Range} (Control Flow); and \texttt{Mutable} (Interface). This yielded 312 methods distributed as shown in Table~\ref{tab:method-distribution}.

\subsection{Experimental Design}

Our evaluation comprises four experimental phases designed to isolate the contribution of formal specifications to test generation quality:

\begin{description}
    \item[Phase 1 (P1) -- Signature Only:] Test generation using only method signatures.
    \item[Phase 2 (P2) -- Signature + Guidance:] Signatures with explicit guidance to cover edge cases.
    \item[Phase 3 (P3) -- Signature + Specification:] Signatures augmented with inferred formal specifications.
    \item[Phase 4 (P4) -- Source Code Baseline:] Full method source code access, providing an upper bound.
\end{description}

We used Google's Gemini 2.0 for test generation (Table~\ref{tab:llm-config}). Temperature 0.3 balances creativity with consistency. We conducted 5 independent runs per method and configuration to account for LLM non-determinism. Prompts were minimal, differing only in specification or source code inclusion (see Supplementary Material, Appendix~D).

\subsection{Metrics}

\paragraph{Specification Quality.}
We measure \emph{precision} (proportion of correct inferred clauses) and \emph{recall} (proportion of expected clauses captured). Specifications are classified by \emph{strength}: strong (both precondition and postcondition non-trivial), partial (one non-trivial), or weak (both trivial).

\paragraph{Test Quality.} We report test count, compilation rate, pass rate, and mutation score (computed using PiTest~\cite{coles2016pitest} with default mutation operators, 10s timeout per test).

\subsection{Manual Validation}

Two authors independently validated specifications for all 312 methods against Javadoc documentation, source code, and standard library specifications. Each clause was labeled as correct, incorrect, incomplete, or overconstrained. Disagreements were resolved through discussion (Cohen's $\kappa$: 0.91 for preconditions, 0.87 for postconditions).

\subsection{Statistical Analysis}

For each metric we report mean, standard deviation, median, IQR, and 95\% bootstrap confidence intervals (10,000 iterations). We use paired $t$-tests (or Wilcoxon signed-rank for non-normal distributions) for phase comparisons, Cohen's $d$ for effect size, and Bonferroni correction for multiple comparisons ($\alpha = 0.05$).

\subsection{Tool Comparisons}

We compared with Jdoctor~\cite{jdoctor2018} (NLP-based exception precondition extraction from Javadoc) and direct LLM-based specification inference (same Gemini 2.0 model prompted to infer JML from source code) on the same 312-method dataset. All materials are available in our replication package.
