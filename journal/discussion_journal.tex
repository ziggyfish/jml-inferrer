\section{Discussion}
\label{sec:discussion}

\subsection{Implications}

Our results demonstrate that heuristic static analysis can automatically generate useful specifications for 99.0\% of methods. These specifications serve as machine-checkable documentation~\cite{peters1998using}, onboarding aids for understanding method contracts~\cite{sillito2008questions}, and API evolution tracking signals~\cite{tip2002practical}. The tool integrates naturally into CI/CD pipelines (pre-commit hooks, pull request analysis, automated test generation) with an average analysis time of 88ms per file.

Our comparison with Jdoctor reveals complementary strengths: Jdoctor excels at recovering documented exceptional behavior from Javadoc, while JML-Inferrer infers specifications from code structure, especially for undocumented methods. A practical workflow might combine both tools to maximize coverage.

Specifications improve test generation because preconditions explicitly state valid input ranges (guiding boundary tests), postconditions define expected outputs (enabling oracles beyond ``does not throw''), and the decomposition allows LLMs to target individual specification clauses rather than reasoning about entire implementations. While source code access (P4) achieves higher absolute scores, the substantial P3 improvement over P1 confirms that specifications encode actionable behavioral information that signatures alone cannot convey.

\subsection{Generalizability}

While evaluated on Apache Commons Lang, the technique is applicable to any Java codebase. Effectiveness depends on code structure (well-structured code produces better specifications), and domain-specific business logic may require extended heuristics. The JML specification format is LLM-agnostic and widely recognized~\cite{leavens2006design}; other LLMs should show similar improvements. Applications span library API specification, legacy code modernization, documentation generation, and runtime verification.

\subsection{Limitations}

\paragraph{Specification coverage gaps.} The ``Other Methods'' category shows the lowest specification strength (42.3\% strong), reflecting difficulty with event handlers, I/O operations, and callbacks. When loop heuristics fail (14.7\% of looping methods), weak specifications reduce test effectiveness by approximately 15~pp. Recent enhancements to \texttt{while}-loop and \texttt{for-each} analysis (counter detection, accumulator and variable-relationship tracking) and the addition of a standard library specification database partially mitigate these gaps, though complex loops involving nested data structures or non-linear counters remain challenging.

\paragraph{Language feature limitations.} Current limitations for object-oriented constructs include inheritance specification conflicts, polymorphic dispatch complicating postcondition inference, and concurrency properties that are not yet analyzed. The new branch-aware conditional postcondition inference (handling \texttt{if/else} returns and ternary expressions) improves postcondition completeness for methods with branching return logic, though deeply nested or multi-branch conditions may still produce conservative results.

\paragraph{False positives.} Although precision is high (94.2\%), the 1.3\% incorrect preconditions could mislead developers or cause false test failures. Mitigation strategies include confidence scoring, automated validation against test suites, and human review for critical methods. Standard library specifications are curated manually, reducing the risk of false positives from method call propagation.
