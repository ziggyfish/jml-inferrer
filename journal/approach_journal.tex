\subsection{Implementation Overview}

\textbf{JML-Inferrer} is implemented in Java 21 (approximately 4,500 LOC) using JavaParser~\cite{javaparser} for AST manipulation. Table~\ref{tab:implementation} summarizes key characteristics. The tool is open-source (Apache License 2.0) and distributed as an executable JAR:

\begin{lstlisting}[language=bash, basicstyle=\ttfamily\small]
java -jar jml-inferrer-1.0.0-jar-with-dependencies.jar <path>
\end{lstlisting}

The tool recursively processes all \texttt{.java} files, adding annotations in-place. It generates 18 annotation types spanning contract specifications, method classifications, nullability, and additional properties (see Supplementary Material, Appendix~A). Unlike traditional JML tools that embed specifications in Javadoc comments, JML-Inferrer generates Java annotations compiled into bytecode and queryable at runtime via reflection.

\subsection{Specification Analysis}

The tool's analysis pipeline comprises three phases: parsing (Phase~1), specification inference (Phase~2), and formatting (Phase~3). We focus here on Phase~2, which contains the core inference logic.

\subsubsection{Heuristic-Based Pattern Matching}

The core analysis uses a visitor pattern over AST nodes with heuristic-based pattern matching. Rather than performing formal symbolic execution~\cite{king1976symbolic, cadar2008klee} or full WP/SP computation (which would require an SMT solver), this pragmatic approach prioritizes scalability and handles common Java idioms effectively~\cite{calcagno2015infer}. Algorithm~\ref{alg:inference} presents the main inference procedure.

\begin{algorithm}[t]
\caption{Specification Inference via Pattern Matching}
\label{alg:inference}
\begin{algorithmic}[1]
\REQUIRE Method AST node $M$
\ENSURE Preconditions $Pre$, Postconditions $Post$, LoopInvariants $LI$
\STATE $Pre \gets \emptyset$; $Post \gets \emptyset$; $LI \gets \emptyset$
\STATE \COMMENT{Infer preconditions from early guards}
\FOR{each statement $S$ in $M$.body}
    \IF{$S$ is null check \texttt{if (p == null) throw/return}}
        \STATE $Pre \gets Pre \cup \{\texttt{p != null}\}$
    \ELSIF{$S$ is range check \texttt{if (p < 0 || p >= n) throw}}
        \STATE $Pre \gets Pre \cup \{\texttt{p >= 0}, \texttt{p < n}\}$
    \ENDIF
\ENDFOR
\STATE \COMMENT{Infer postconditions from return statements}
\FOR{each \texttt{return $e$} in $M$.body}
    \IF{$e$ is field access \texttt{this.f}}
        \STATE $Post \gets Post \cup \{\texttt{\textbackslash result == this.f}\}$
    \ELSIF{$e$ is new object \texttt{new T(...)}}
        \STATE $Post \gets Post \cup \{\texttt{\textbackslash result != null}\}$
    \ELSIF{$e$ involves \texttt{\textbackslash old} pattern}
        \STATE $Post \gets Post \cup \{$derive relationship$\}$
    \ENDIF
\ENDFOR
\STATE \COMMENT{Infer conditional postconditions from branching returns}
\FOR{each \texttt{if-else} or ternary in $M$.body with returns in both branches}
    \IF{both branches return literals $a$, $b$}
        \STATE $Post \gets Post \cup \{\texttt{\textbackslash result == $a$ || \textbackslash result == $b$}\}$
    \ELSIF{condition is null check on parameter $p$}
        \STATE $Post \gets Post \cup \{\texttt{$p$ != null ==> \textbackslash result != null}\}$
    \ENDIF
\ENDFOR
\STATE \COMMENT{Infer loop invariants}
\FOR{each loop $L$ in $M$.body}
    \STATE $LI \gets LI \cup \text{InferLoopInvariant}(L)$
\ENDFOR
\RETURN $(Pre, Post, LI)$
\end{algorithmic}
\end{algorithm}

\subsubsection{Loop Invariant Inference}
\label{subsec:loop-heuristics}

The tool employs four heuristics for loop invariant inference: (1)~bound-based invariants for standard \texttt{for} loops, (2)~accumulator pattern detection, (3)~monotonicity detection from update expressions, and (4)~bounded symbolic unrolling (3 iterations) as a fallback. When all heuristics fail, the tool produces a conservative ``weak specification.'' On the 68 loops across 48 methods in our evaluation dataset, overall success rate was 85.3\% (details in Supplementary Material, Appendix~B).

These heuristics extend beyond \texttt{for} loops. For \texttt{while} loops, the tool detects counter variables from body assignments (e.g., \texttt{i++}, \texttt{i += n}), extracts bounds from the loop condition, and reuses the same accumulator and variable-relationship analyses available to \texttt{for} loops. Common iterator idioms (\texttt{while (iter.hasNext())}) are also recognized. For enhanced \texttt{for-each} loops, the tool infers element membership invariants and applies variable-relationship analysis (e.g., max/min tracking) to the loop body, producing richer invariants than a condition-only approach.

\subsubsection{Interprocedural Analysis}
\label{subsec:method-calls}

Method calls are handled in two passes. In the first pass, methods are analyzed independently with results cached. In the second pass, specifications propagate across call boundaries: methods with existing specifications or \texttt{@Pure} annotations are used as-is; standard library methods use a predefined specification database; unknown methods receive conservative assumptions (may throw, may modify accessible state, unconstrained return).

The standard library specification database (\texttt{StandardLibrarySpecs}) provides pre-defined JML contracts for commonly used Java API methods across \texttt{String} (e.g., \texttt{charAt} bounds, \texttt{substring} range constraints, \texttt{trim} non-null guarantee), \texttt{Math} (e.g., \texttt{abs} non-negativity, \texttt{max}/\texttt{min} relational bounds), \texttt{List} and \texttt{Map} (e.g., \texttt{get} index bounds, \texttt{size} non-negativity, \texttt{add} size increment), and utility classes (\texttt{Objects.requireNonNull}, \texttt{Arrays.copyOf}, \texttt{Integer.parseInt}). When cache lookup fails for a method call, the tool consults this database and propagates matching preconditions and postconditions by mapping generic parameter names to the actual call arguments.

Object dereferences generate definedness conditions (\texttt{obj != null}), with chains generating conjunctions. Array accesses generate non-null and bounds constraints.

\subsection{Specification Formatting and Simplification}

Inferred specifications are formatted as Java annotations and added to the method's AST node. The formatter applies algebraic simplification, constant folding, trivially-true condition removal, and range analysis to combine redundant constraints.

\subsection{Categorization of Method Types}
\label{subsec:categorization}

To systematically evaluate specification inference across diverse implementations, we developed a categorization taxonomy building on method stereotypes~\cite{dragan2006reverse} (inter-rater reliability: Cohen's $\kappa = 0.87$). Methods are automatically categorized as: \textbf{Accessors \& Mutators} (field read/write), \textbf{Control Flow} (conditionals and loops), \textbf{Factory \& Delegate} (object creation and forwarding), \textbf{Utility} (static helpers), \textbf{State Modification} (field modification with logic), or \textbf{Other} (event handlers, callbacks). When multiple patterns match, the most specific category is selected.
